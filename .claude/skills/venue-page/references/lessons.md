# venue-page: уроки и разборы (вынесено из SKILL.md 05.11.2026 без правок текста)

Читать, когда прогон ломается или нужен рецепт для комплекса из нескольких залов.

## Экономия — правила, выведенные из потерь 13.09.2026

Больше половины расхода той сессии — фаза написания, запущенная трижды
и трижды не дописанная (два прерывания пользователя убили воркфлоу с
агентами, третий заход упал на 403 от Sonnet). Отсюда:

1. **Текст пишет оркестратор, не субагент.** Пока пользователь рядом и
   может нажать Esc, любой субагент — это ставка, которую можно потерять
   целиком. Субагенты только там, где потеря дешёвая: обход сайта, факты.
2. **Никаких `sleep`-циклов.** Каждый возврат из ожидания стоит полного
   контекста оркестратора. Фоновые скачивания и `prep-photos` запускать
   первыми, делать другое, проверить один раз в конце.
3. **Firecrawl с HTML — только в файл и только через скрипт.** Карты
   отдают 1–3 МБ; если результат попал в чат — это уже ошибка. Формат
   `html`, и сразу `maps-reviews.mjs` по сохранённому файлу.
4. **Кадры смотреть контактным листом**, один `magick montage` и один
   Read на площадку, не по одному файлу.
5. **Не перечитывать код.** Всё, что нужно для текста, лежит в этом
   скилле и в `facts.json`; `venues.ts` открывать только строки типа
   (1–160) — не весь файл.
6. **Воркфлоу не возобновлять по `scriptPath` из проектной папки** —
   путь режется валидатором; либо `script` инлайн с `resumeFromRunId`,
   либо вовсе без воркфлоу (одна площадка = один заход оркестратора).
7. **Гео — из HTML Карт**, не искать и не геокодировать (см. фазу 1а).

Ориентир расхода на одну площадку при таком порядке: Haiku ×2 фоном
(сайт, факты) + один контактный лист + один JSON + `verify` + сборка.


### Комплекс из нескольких залов (Гребнево, 17.09.2026)

Одна организация с несколькими площадками — **одна карточка каталога**,
не девять: адрес, банкетная служба и общие условия одни. Залы лежат в
`venue.halls` (тип `VenueHall`: id, name, kicker, photos, areaM2, areaNote,
banquet, buffet, tariff по дням, included, body), страница — блоки
`stats → halls-index → halls → statement (усадьба) → terms (общие условия)
→ gallery → reviews → faq`. Материалы: у каждого зала своя ссылка на диск —
`yadisk-previews`/`yadisk-pick` со слагом-путём `research/<slug>/<зал>`,
`prep-photos research/<slug>/<зал>`, в JSON пути `/venues/<slug>/<зал>/pNN.webp`
(`verify-venue` и `place-photos` ищут кадр в `research/<slug>/<зал>/photos/`).
Сборка JSON — генератором `research/<slug>/build.mjs` (тексты + тарифы из
`facts.json` + манифесты залов), не руками: 100 кадров с подписями.
В ленте (`feed.ts`) — вместимость по самому большому залу, чек — общий
минимум меню; `pb-seed` считает то же сам из `halls`.

Сцена (`VenueScene`): `layout` `split` (по умолчанию, кадр 4:5 → портрет),
`wide` (широкий кадр во всю ширину → горизонтальный кадр), `gallery`
(лента 2–5 кадров, когда одного мало: сервировка, декор от свадьбы к свадьбе).
Подряд одинаковые `split` утомляют — чередовать.


## Что ломалось (дописывать после каждого прогона)

- 2026-09-13: `cloud-api.yandex.net` по IPv4 не отвечает (таймаут), по IPv6 работает: у curl без -4
  проходит — в `fetch-yadisk` стоят ретраи и `--dns-result-order=ipv6first`.
  Не помогло — качать `curl -L` по ссылкам `file` из листинга.
- 2026-09-13: во второй ссылке на диск для одной площадки может лежать
  та же папка или ролики (.mov) — перед `prep-photos` смотреть содержимое;
  видео в карточку сейчас не идёт, лежит в сырье до захода по docs/VIDEO.md.
- 2026-09-13: прерывание оркестратора (Esc / «стоп» пользователя) убивает
  и агентов воркфлоу. Возобновлять `Workflow` с `resumeFromRunId` и скриптом
  инлайн (`script`), не `scriptPath` из проектной папки — тот путь режется
  проверкой разрешений.
- 2026-09-13: агент «материалы» не должен ждать фоновые скачивания —
  фото пережимает оркестратор до запуска воркфлоу, агент только читает
  `photos.json`.
- 2026-09-13: Firecrawl на Картах с `formats: ["json"]` + промпт вернул
  мусор (2 отзыва с кракозябрами) — извлекать только из `html` скриптом.
- 2026-09-13: Sonnet может отдать 403 (лимит аккаунта) — тогда фазу 3 пишет
  оркестратор сам. Выбор кадров без просмотра каждого файла: контактный лист
  `magick montage research/<slug>/photos/p*.webp -thumbnail 200x200 -set label
  '%t' -tile 10x -geometry +4+4 research/_sheets/<slug>.jpg` и один Read.
- 2026-09-13: новая площадка должна попасть и в `src/data/feed.ts` (лента
  каталога строится из него, не из VENUES) — с рейтингом из reviews и без
  `checkFrom`, если прайса нет. Подборки в `articles.ts` ссылаются на
  площадки по имени — проверять после переименований.
- 2026-09-13: `seo.ogImage` → `/venues/<slug>/og-cover.jpg`, файл нужен и в
  `public/` (og:image через `new URL`), и в `src/assets/` (verify/place ищут
  все пути JSON). Делать `magick <hero> -resize 1200x1200\> -quality 85`.
- 2026-09-17: девять дисков Гребнево (364 файла) целиком не качали — превью
  через `yadisk-previews` (слаг со слэшем = готовый путь, как в prep-photos),
  один контактный лист на зал, `yadisk-pick` по номерам. Диск отдаёт
  оригиналы по одному, ~10 минут на 100 кадров — запускать фоном первым.
- 2026-09-17: у поля `photos` в PocketBase был потолок 99 файлов, у усадьбы
  102 — миграция `1757700300_venue_photos_cap.js` поднимает до 300; после
  новой миграции локальный PB перезапустить (накатывается при старте).
- 2026-09-17: Карты у Гребнево отдают адрес без улицы («территория усадьба
  Гребнево») — так и пишем, не додумываем.
- 2026-09-17: в галерее «Отражения» полтора месяца жили десять чужих
  картинок со страницы-источника: стоковые аватарки отзывов (206×206),
  иконка, прозрачные лого-подложки и три посторонних стока (документы,
  шлемы, мозговой штурм). `fetch-urls` тянет со страницы ВСЕ картинки
  подряд, а остаток кадров ушёл в `gallery` пачкой под один alt
  «<Имя> — фото площадки» — то есть их никто не отбирал. Нашёл заказчик:
  из галереи карточки эти кадры уезжают ещё и в доску главной наравне
  с залом. `verify-venue` теперь ловит это сам (п. 5: мелкие картинки,
  прозрачность = графика, ≥3 кадров под одним alt), но правило прежнее:
  в `gallery` идут только отобранные кадры, и у каждого свой alt.
- 2026-10-05 (Villa Barvikha): `prep-photos` на кадрах 7000 px с Sony через
  раз писал обрезанный webp — каждый прогон другие кадры, а `identify`
  (читает только заголовок) этого не видел. В скрипт добавлены три попытки
  и полное декодирование результата (`magick -regard-warnings f null:`).
- 2026-10-05: у площадки на Картах заведён только дом, без организации —
  отзывов нет. `rating`/`reviews` в `feed.ts` теперь необязательные: без
  них звезда «0,0» не рисуется ни в каталоге, ни в первом экране, ни в сравнении.
- 2026-10-05: две сессии подряд обрывались посреди выгрузки. Сервер своё
  успевает (кадры остаются в `/srv/wed-research/out/<slug>/raw`), рвётся
  только перенос на ноутбук — повторять `research.sh pull <slug> raw`,
  а не `pick`: с Диска заново качать не нужно.
- 2026-10-05: ссылка «Яндекс.Карты» в таблице может вести на ДОМ
  (`/maps/…/house/…`), а не на организацию — у дома отзывов нет, и площадку
  с 368 отзывами чуть не выпустили «без отзывов». Org-URL искать поиском

  на этом, оригиналы — экспортом канала из Telegram Desktop. Ссылки на
  ролики канала живут сутки — брать свежие (`t.me/s/<канал>` через
  Firecrawl `rawHtml`, с ноутбука t.me не открывается). Ссылка реестра

  `build.py` должен прогонять сам (замена — функцией, не строкой

  Брать `formats: ["rawHtml"]` и переложить поле: `{html: d.rawHtml}`.
