# venue-page — конвейер карточки площадки

Цель: из строки таблицы (название, сайт, ссылка на материалы, Яндекс.Карты)
получить `src/data/venues/<slug>.json` + фото в `src/assets/venues/<slug>/`,
после чего страница `/moskva/ploshchadki/<slug>/` собирается сама.

Главный принцип: **нет единого шаблона страницы.** Тело карточки — список
типизированных блоков `blocks` (тип `VenueBlock` в `src/data/venues.ts`),
и порядок блоков подбирается под площадку: у ресторана на первом месте кухня
и депозит, у оранжереи — стекло и парк, у зала с открытым прайсом — таблица
по дням недели. Новых типов блоков агенты не выдумывают: только реестр ниже.
Нужен новый тип — это отдельная задача оркестратора (компонент + тип + этот файл).

## Роли (пересмотрены после аудита 13.09.2026)

| Фаза | Кто | Почему |
| --- | --- | --- |
| 0. Материалы | скрипты, без токенов, ДО запуска моделей | скачать/пережать — механика |
| 1. Исследование | Haiku 4.5, фоновый субагент | обход сайта, выгрузка сырья; потерять не жалко |
| 1а. Отзывы и гео | скрипт `maps-reviews` | из HTML Карт, модель не видит страницу |
| 2. Факты | Haiku 4.5, фоновый субагент | извлечение по схеме, без творчества |
| 3. Концепция и текст | **оркестратор сам** | см. «Экономия» ниже |
| 4. Проверка | скрипт `verify-venue` + чтение оркестратора | цифры, фото, типографика, сборка |

## Экономия — правила, выведенные из потерь 13.09.2026

Больше половины расхода той сессии — фаза написания, запущенная трижды
и трижды не дописанная (два прерывания пользователя убили воркфлоу с
агентами, третий заход упал на 403 от Sonnet). Отсюда:

1. **Текст пишет оркестратор, не субагент.** Пока пользователь рядом и
   может нажать Esc, любой субагент — это ставка, которую можно потерять
   целиком. Субагенты только там, где потеря дешёвая: обход сайта, факты.
2. **Никаких `sleep`-циклов.** Каждый возврат из ожидания стоит полного
   контекста оркестратора. Фоновые скачивания и `prep-photos` запускать
   первыми, делать другое, проверить один раз в конце.
3. **Firecrawl с HTML — только в файл и только через скрипт.** Карты
   отдают 1–3 МБ; если результат попал в чат — это уже ошибка. Формат
   `html`, и сразу `maps-reviews.mjs` по сохранённому файлу.
4. **Кадры смотреть контактным листом**, один `magick montage` и один
   Read на площадку, не по одному файлу.
5. **Не перечитывать код.** Всё, что нужно для текста, лежит в этом
   скилле и в `facts.json`; `venues.ts` открывать только строки типа
   (1–160) — не весь файл.
6. **Воркфлоу не возобновлять по `scriptPath` из проектной папки** —
   путь режется валидатором; либо `script` инлайн с `resumeFromRunId`,
   либо вовсе без воркфлоу (одна площадка = один заход оркестратора).
7. **Гео — из HTML Карт**, не искать и не геокодировать (см. фазу 1а).

Ориентир расхода на одну площадку при таком порядке: Haiku ×2 фоном
(сайт, факты) + один контактный лист + один JSON + `verify` + сборка.

## Папки

```
research/<slug>/            (в .gitignore — сырьё в репозиторий не едет)
  raw*/                     скачанные оригиналы (Яндекс.Диск, Drive, сайт)
  photos/pNN.webp           пережатые кадры для выбора
  photos.json               манифест: id, ширина, высота, ratio, orientation, kb
  site/<page>.md            markdown страниц сайта площадки (Firecrawl)
  notes.md                  текст из таблицы, что прислал заказчик, как есть
  facts.json                извлечённые факты (фаза 2)
  concept.md                концепция (фаза 3): ключевые идеи и порядок блоков
src/data/venues/<slug>.json итог
src/assets/venues/<slug>/   только кадры, на которые ссылается JSON
public/venues/<slug>/og-cover.jpg
```

## Фаза 0 — материалы (скрипты)

```
node --dns-result-order=ipv6first scripts/fetch-yadisk.mjs <public_url> research/<slug>/raw
gdown --folder <drive_url> -O research/<slug>/raw          # Google Drive
node scripts/prep-photos.mjs <slug>                          # → photos/ + photos.json
```

Фото с сайта площадки (когда папки с материалами нет): Haiku в фазе 1
собирает ссылки на картинки из `links`/`html` Firecrawl, скрипт качает их
в `raw-site/`, дальше тот же `prep-photos`. Кадры меньше 1200 px по длинной
стороне в героя и сцены не ставить — только в доску.

`prep-photos` сам отбрасывает битые файлы (`magick identify` падает) и
помечает их `broken: true` — на такие ссылаться нельзя.

### Видео (обязательный шаг, не «потом»)

Ролики площадки — такие же материалы, как фото; без них карточка
неполная. Где искать: подпапки диска («ВИДЕО …» внутри выборки —
`fetch-yadisk` обходит их рекурсивно, `--only=video` качает только их),
вторая ссылка на диск, видеопрезентация в Google Drive (`gdown "https://drive.google.com/uc?id=<id>"`).

1. Кадр из каждого ролика одним листом: `ffmpeg -ss 3 -i <файл> -frames:v 1
   -vf scale=240:-2 vid/vNN.jpg` → `magick montage … -tile 7x`. Один Read.
2. Берём **рилсы как есть**, с плашками и текстом — это живой контент
   площадки. Не берём: переписку в чате, скриншоты карт, чужую рекламу.
3. `node scripts/prep-video.mjs <slug> public/venues/<slug> src/assets/venues/<slug> <src1>@<сек> …`
   → `reel-NN.mp4` (720×1080, 8 с, звук) в public и постер `reel-NN.webp`
   в src/assets. Горизонтальный исходник кропится по центру.
4. В `src/data/reels.ts` — запись на каждый ролик с `venue: '<slug>'`,
   `sound: true` (если дорожка есть) и `alt`. Плитка на доске главной
   ведёт на карточку площадки сама.
5. В JSON площадки: 1–2 ролика вторым и пятым кадром `gallery` (первый
   экран их играет), блок `{ "type": "reels", "title": "Видео" }` после
   `gallery`. В доску галереи ролики не попадают — страница их отфильтрует.

## Фаза 1 — исследование (Haiku)

1. `firecrawl_map` по сайту площадки → список URL. Берём страницы про зал,
   территорию, меню/кухню, цены/условия, контакты, FAQ, «о нас». Не берём
   блог-новости, политику конфиденциальности, страницы других площадок оператора.
2. Каждую — `firecrawl_scrape` (`formats: ["markdown"]`, `onlyMainContent: true`)
   → `research/<slug>/site/<имя>.md`. Сохранять как есть, не пересказывать.
3. Ссылку Яндекс.Карт — `firecrawl_scrape` с `formats: ["markdown","links"]`,
   `waitFor: 3000`. Оттуда: полный адрес, рейтинг, число оценок и отзывов,
   часы, телефон, первые отзывы с текстом → `site/maps.md`. Не открылось —
   записать «карты не отдали данные», не гадать.
4. Текст из таблицы (колонка «Текстовое описание») → `notes.md` дословно.
5. Если у площадки PDF-прайс/техрайдер — `firecrawl_scrape` с `parsers: ["pdf"]`,
   сам PDF сохранить в `research/<slug>/docs/` (в `public/docs/` кладёт оркестратор).

## Фаза 1а — отзывы с Яндекс.Карт (оркестратор, без модели)

Отзывы не собирает агент — их вытаскивает скрипт из HTML. Порядок:

1. Короткую ссылку из таблицы раскрыть в org-URL: `curl -s -o /dev/null -w "%{redirect_url}" <ссылка>` →
   `https://yandex.ru/maps/org/<name>/<id>/`.
2. `firecrawl_scrape` на `…/<id>/reviews/` с `formats: ["html"]`,
   `location: {country: "RU", languages: ["ru-RU"]}`, `waitFor: 4000` и
   `actions` из 2–3 прокруток вниз с паузами 1500 мс и финальным `scrape`.
   Без RU-локации и прокрутки страница отдаёт скелет без отзывов.
   Результат Firecrawl большой (1–3 МБ) и ложится в файл `tool-results/…txt`.
3. `node scripts/maps-reviews.mjs <тот файл> <slug>` → `research/<slug>/reviews.json`.
   Полный текст берётся из JSON-состояния страницы (в разметке длинные
   отзывы свёрнуты до ~200 знаков, «Ещё» догружает по клику); скрипт сам
   выбирает самый длинный html из ответа (верхний бывает скелетом, полный
   в `actions.scrapes`). Если в выводе «отзывы взяты из разметки» — тексты
   обрезаны, страницу надо перетянуть с прокруткой.
   Далее
   потом копия в `src/data/reviews/<slug>.json` (только поля author, date, iso,
   rating, text). Скрипт сам оставляет **20 последних** — больше не храним.
   Агрегат (рейтинг, число оценок, число отзывов) берётся из og:description
   страницы, целиком с Карт.
4. Если у площадки нет своей точки на Картах (LЁD живёт под карточкой
   «Спарк» оператора) — берём файл оператора под slug площадки.
5. **Координаты — из того же HTML**, ничего не искать и не геокодировать:
   `grep -o 'data-coordinates=\\"[0-9.]*,[0-9.]*'` даёт `lon,lat` метки
   организации. Записать в `facts.json → location.geo {lat, lon}` ДО фазы 3,
   агент написания просто переносит в `contacts.geo`. Координаты из
   параметра `ll=` короткой ссылки не брать: при `mode=search` это центр
   выдачи, а не точка.

Страница читает `src/data/reviews/*.json` через `venue-reviews.ts`; первый
экран и лента берут рейтинг оттуда же. Тот же файл — будущая запись
`venue_reviews` в PocketBase.

`source` (имя файла в `site/`). Схема:

## Фаза 3 — концепция и текст (Sonnet)

Вход: `facts.json`, `photos.json`, `notes.md`, два готовых примера
(`riverLoft`, `forestDew` в `src/data/venues.ts`) — только как образец тона
и плотности, НЕ как структура.

1. Сначала `concept.md`: 3–5 ключевых идей площадки (что у неё есть такого,
   чего нет у соседей по каталогу), какой порядок блоков это подчёркивает и
   почему, какие кадры под каждую сцену. Идеи берутся из `uniqueClaims`
   и фактов, не из общих слов про «атмосферу».
2. Потом `venue.json` по типу `Venue` (см. схему ниже).

### Реестр блоков (тип `VenueBlock`)

| type | Когда | Компонент |
| --- | --- | --- |
| `stats` | 3–4 крупные цифры, которые есть в фактах | StatsStrip |
| `scenes` | главный модуль: группа сцен «кадр + текст», можно несколько групп с разными заголовками | ScrollyScenes |
| `statement` | мысль без кадра: формат работы, история, устройство прайса; `dark: true` — инверсия | VenueStatement |
| `terms` | прайс / входит / за доплату; без открытых цен — `title` без обещания цифр | VenueTerms |
| `rules` | ограничения, тёмная секция | VenueRules |
| `docs` | PDF для подрядчиков (файл в public/docs/) | VenueDocs |
| `gallery` | доска всех кадров; без `photos` берёт `venue.gallery` | PhotoMasonry |
| `reviews` | отзывы из venue-reviews.ts; нет — блок пропадает сам | Reviews |
| `reels` | ряд роликов площадки из data/reels.ts (venue = slug); нет роликов — не рисуется | ReelsRow |
| `halls-index` | комплекс из нескольких залов (усадьба): плитка-оглавление залов из `venue.halls` — номер, тип, имя, гостей, аренда «от»; ведёт на якорь секции | HallsIndex |
| `halls` | секции залов по порядку `venue.halls`: рельс кадров, три числа, тариф по дням недели, что входит, 1–2 абзаца; общие условия — один раз в `terms` ниже | VenueHalls |
| `faq` | 4–7 вопросов, ответы только из фактов | FaqBlock |

### Комплекс из нескольких залов (Гребнево, 17.09.2026)

Одна организация с несколькими площадками — **одна карточка каталога**,
не девять: адрес, банкетная служба и общие условия одни. Залы лежат в
`venue.halls` (тип `VenueHall`: id, name, kicker, photos, areaM2, areaNote,
banquet, buffet, tariff по дням, included, body), страница — блоки
`stats → halls-index → halls → statement (усадьба) → terms (общие условия)
→ gallery → reviews → faq`. Материалы: у каждого зала своя ссылка на диск —
`yadisk-previews`/`yadisk-pick` со слагом-путём `research/<slug>/<зал>`,
`prep-photos research/<slug>/<зал>`, в JSON пути `/venues/<slug>/<зал>/pNN.webp`
(`verify-venue` и `place-photos` ищут кадр в `research/<slug>/<зал>/photos/`).
Сборка JSON — генератором `research/<slug>/build.mjs` (тексты + тарифы из
`facts.json` + манифесты залов), не руками: 100 кадров с подписями.
В ленте (`feed.ts`) — вместимость по самому большому залу, чек — общий
минимум меню; `pb-seed` считает то же сам из `halls`.

Сцена (`VenueScene`): `layout` `split` (по умолчанию, кадр 4:5 → портрет),
`wide` (широкий кадр во всю ширину → горизонтальный кадр), `gallery`
(лента 2–5 кадров, когда одного мало: сервировка, декор от свадьбы к свадьбе).
Подряд одинаковые `split` утомляют — чередовать.

### Фото

- Пути только вида `/venues/<slug>/pNN.webp` (имена из `photos.json`),
  `hero.image` и `seo.ogImage` — `/venues/<slug>/og-cover.jpg` не нужен:
  ставим лучший кадр `.webp`, оркестратор сделает og-обложку сам.
- `hero.image` — вертикальный или квадратный кадр (`orientation` в манифесте),
  первый экран — окно 4:5. `hero.portrait` — второй вертикальный.
- Сцена `split` → portrait; `wide` → landscape; `gallery` → любые, лучше portrait.
- `gallery` (доска) — **40–50 кадров** (заказчик, 17.09.2026: «12–18» было
  мало): все годные кадры из `photos.json`, включая те, что стоят в сценах
  и в герое, — доска не второй отбор, а весь материал площадки. На странице
  сразу видно 12, остальные по кнопке «Показать все» (PhotoGallery),
  так что длина доски страницу не растягивает. `wide: true` у горизонтальных.
- Битые (`broken: true`) и кадры уже 1200 px в героя и сцены не ставить.
- Один кадр не повторять в двух сценах; герой может повторяться в доске.

### Текст — правила, за которые режут

- Тон: спокойный, конкретный, по делу; как `riverLoft`. Без «уникальной
  атмосферы», «незабываемых моментов», «идеального места». Первое предложение
  сцены — факт, а не эпитет.
- **Ни одной цифры, которой нет в `facts.json`.** Скрипт проверки сверяет
  каждое число с сырьём и роняет прогон.
- Нет прайса — так и пишем: «Цены по запросу» в `terms` с `title`
  «Как забронировать» и без выдуманных вилок.
- Жирности, `<b>`, капса нет нигде. Названия своих секций — без капса.
- Висячие предлоги: короткие слова клеим ` ` к следующему
  (в JSON — символ ` `, не HTML-сущность). Кавычки «ёлочки», тире «—».
- `kicker`: тип + один топоним, до 32 знаков («Оранжерея · Быково»).
- `lead`: 2–3 предложения, что это за место и где, с километрами от МКАД.
- `alt` — что на кадре по-русски, без «фото площадки».
- `seo.title`: «Имя — тип в месте · WED Secrets», `seo.description` до 160 знаков.
- Пункты списков — без тире в начале, без точки в конце.

### Обязательные поля JSON помимо `blocks`

Тип `Venue` требует и плоские поля — их читают каталог, сравнение и карта:
`slug, citySlug: "moskva", city: "Москва и область", category: "Площадки",
categorySlug: "ploshchadki", name, kicker, title, lead, hero, meta (4 строки:
Вместимость · Площадь · Форматы · Кухня), stats, scenes, terms, included,
extras, rules, gallery, faq, contacts (address, addressNote, geo, phone,
phoneHref, email, hours, routes, links), seo`.
Поля `scenes, terms, included, extras, rules, faq` при наличии `blocks`
страница не читает — оставляем их пустыми массивами `[]`, дублировать
содержимое блоков туда не нужно. Живыми остаются `stats`, `gallery`, `meta`,
`contacts`, `hero`: их читают каталог, карта, сравнение и первый экран.
`contacts.geo` — координаты точки, взять из карт/сайта; без них площадка
не попадёт на карту каталога.

## Фаза 4 — проверка и сборка (оркестратор)

```
node scripts/verify-venue.mjs <slug>   # структура, фото, цифры против сырья, типографика
node scripts/place-photos.mjs <slug>   # кадры из JSON → src/assets (+og в public)
npx astro build                        # 0 ошибок, страница /moskva/ploshchadki/<slug>/ есть
```

Haiku-проверка после скрипта: прочитать `venue.json` и `facts.json`,
найти утверждения (не только цифры), которых нет в фактах, и отчёт списком.
Финальное чтение — оркестратор: тон, повторы, порядок блоков против `concept.md`.

Отзывы: если `facts.reviews.items` не пустой — оркестратор добавляет запись
в `src/data/venue-reviews.ts` (формат там), тогда блок `reviews` оживает.
