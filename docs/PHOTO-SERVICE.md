# Сервис фото — задача (06.11.2026)

## Зачем

Принцип из `CLAUDE.md`: **фото готовится один раз — когда попадает к нам, а не когда
его смотрят. Программа страниц фото не режет.**

С 05.11 страницы каталога рисует служба `wedsecrets-ssr` (сайт из базы), и она же режет
фото под размеры экрана (`/_image`, sharp) при первом просмотре. Итог 05–06.11: 43 падения
службы по памяти за сутки, у заказчика — битые кадры и растянутое фото, первый посетитель
ждёт нарезки. 06.11 на сервере поставлена настройка памяти (`docs/DEPLOY.md`, «Память
службы») — падения ушли, но устройство осталось неправильным: страницы и нарезка в одной
программе, нарезка — в момент просмотра, фото из сборки режутся второй раз.

## Решения Никиты (06.11)

1. **Отдельный инструмент для фото.** Кандидат — imgproxy (открытый, libvips, ровная
   память, отдельный процесс: его сбой не роняет страницы). Перед выбором — официальная
   документация; сверить память на 2 ГБ сервера, формат адресов (подпись), webp/avif,
   кэш nginx перед ним (как `wedimg`, 30 дней).
2. **Резать по «Готово».** Подрядчик нажал «Готово» (ревизия ушла на модерацию) —
   нарезка всех размеров его кадров начинается сразу. Модерация дольше нарезки
   (карточка 50 фото × ~5 ширин ≈ 250 вариантов, по одному — порядка 2–3 минут),
   поэтому к одобрению всё готово. Вернули или удалили — ничего страшного: лишние
   варианты выпадут из кэша сами (`inactive=30d`). Одобрили раньше, чем нарезалось, —
   карточка ждёт готовности фото (минуты), а не выходит с пустыми кадрами.
   То же — для карточек конвейера (`pb-seed*` с `--publish`).
3. **Второй раз не резать.** Фото из `src/assets`, уже нарезанные при сборке
   (`/_astro/*`), страницы с сервера должны отдавать готовыми файлами, а не через
   повторную нарезку. Сейчас: на SSR-страницах даже такие кадры идут через `/_image`.

## Как устроено (07.11.2026, ветка `claude/photo-service`)

Выбор — imgproxy 4.0.22 (открытая версия). Сверено с docs.imgproxy.net: готовых пакетов
нет, .deb выгружается из их образа (`.github/workflows/imgproxy-package.yml`); своего
кэша в бесплатной версии нет — хранит nginx; адреса с 127.0.0.1 запрещены, пока не
включён `IMGPROXY_ALLOW_LOOPBACK_SOURCE_ADDRESSES`.

- **Адрес варианта** — `/ph/<ширина>/<вид>/<путь>`, строит его только
  `src/lib/photo-url.mjs` (им пользуются и страницы, и обработчик). Виды: `a` — кадр
  сборки (`/_astro/*`), `f` — файл базы, `p` — превью анкеты. Ширины — лестница
  `PHOTO_WIDTHS` (объединение `IMG_WIDTHS`); ширина srcset округляется вверх до ступени.
- **Страницы.** `src/lib/photo-service.ts` — внешняя служба картинок Astro, включается
  `PHOTO_SERVICE=1` (deploy.yml). С ней Astro фото не режет ни при сборке (сборка
  ~1,5 мин вместо 5–7, `_astro` ~0,7 ГБ вместо ~2 ГБ), ни на сервере. `astro dev`
  и локальная сборка без переменной — обычный sharp.
- **imgproxy** — служба `imgproxy` на 127.0.0.1:8081, свой пользователь, `MemoryMax=400M`,
  2 потока, только webp. Оригиналы видит только на чтение (`BindReadOnlyPaths`:
  `site` → `/var/www/wedsecrets/_astro`, `pb` → хранилище базы). Без подписи, но
  `IMGPROXY_ONLY_PRESETS` (только наши ширины) и `IMGPROXY_ALLOWED_SOURCES` (только наш
  диск и превью базы). Конфиги — `deploy/photo/`.
- **Хранение — файлами, навсегда.** nginx ищет вариант в `/srv/wedsecrets-photos/store/`;
  нет — режет imgproxy, nginx сохраняет (`proxy_store`). Файл базы лежит по одному
  имени (`<ширина>/f/<имя>`), без коллекции и записи. Наружу — только коллекции
  карточек (specialists, venues); кадры ревизий режет лишь внутренний адрес
  127.0.0.1:8088. Превью не хранится, только кэш `wedphp` на час.
- **По «Готово».** Хук (`queuePhotos` в `cabinet.js`) кладёт список кадров ревизии
  в `/srv/wedsecrets-photos/queue/`; то же — при сохранении карточки (одобрение,
  `pb-seed --publish`, площадки). Обработчик `scripts/photo-worker.mjs` (служба
  `wedsecrets-photo`) режет все ширины по одному. Раз в 10 минут — обход всех кадров
  сборки и карточек: пропущенное дорежется само.
- **Имена при одобрении.** `approve()` копирует файлы ревизии в карточку с тем же
  именем (`getReuploadableFile(…, true)`), уже бывшие у карточки кадры не копирует
  вовсе — нарезанное по «Готово» находится после одобрения. `startEdit` тоже
  сохраняет имена. Проверено на тестовой базе 0.40.4: имя кадра ревизии и карточки
  совпадает.

  `src/lib/live-data.ts` (кадры из базы), `astro.config.mjs` (`image`),
  компоненты с `<Image>` на SSR-страницах.
- Хук «Готово» — `pb/pb_hooks/lib/cabinet.js` (отправка ревизии); заливка хуков —
  только по правилу `docs/DEPLOY.md` (свежий master → `pb-test-cabinet` → scp → md5).
- Сервер: nginx `/etc/nginx/sites-available/wedsecrets` (`location ^~ /_image`),
  кэш `/etc/nginx/conf.d/wed-cache.conf`; любые правки сервера — с копией, план
  Никите до правки.
- После перехода: убрать `scripts/warm-images.sh` и шаг прогрева в `deploy.yml`
  (сделано 07.11 в ветке), строку «Память службы» в `docs/DEPLOY.md` переписать по факту.
