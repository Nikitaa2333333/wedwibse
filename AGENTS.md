# WED Secrets — правила проекта

## Что это

Свадебный онлайн-сервис WED Secrets (wed-secrets.ru). Сейчас фаза «дизайн прежде всего»:
Не путать с wedwed.ru — это конкурент, его разбор лежит в `SEO.md`.
собираем визуальный язык по референсам пользователя. Форма-анкета отложена.

## Масштаб продукта (держать в голове с первой строки кода)

Это не лендинг, а **свадебный агрегатор** площадок и подрядчиков Москвы и МО
с серьёзной функциональной частью: куча фильтров, посадочные страницы как главный
SEO-инструмент, в будущем — личный кабинет, CRM/менеджер, монетизация.
Полное понимание задачи — в гуглдоке «Свадебный агрегатор — понимание задачи»
(и в памяти проекта, файл `wedwibse-product.md`).

Порядок работ: **сначала дизайн, потом архитектура функциональности.**
Дизайн, который делаем сейчас, ляжет на эту архитектуру — поэтому уже на этапе
дизайна запрещено всё, что потом помешает:

- **Скорости сайта.** Никаких тяжёлых библиотек и клиентских фреймворков ради
  красоты: моушн — CSS + уже подключённые Lenis/GSAP, без новых зависимостей
  «за компанию». Каждая новая клиентская зависимость — только с обоснованием.
- **SEO.** Контент — статикой/с сервера в HTML, не рисуется клиентским JS.
  Семантическая разметка (заголовки, списки, ссылки) — сразу, а не «потом причешем».
- **Расширению до каталога.** Секции проектировать как переиспользуемые модули:
  карточка площадки, полоса фильтров, блок «текст + список» станут телом
  посадочных страниц. Ничего намертво привязанного к одной странице.
- **Фиксированному SEO-фундаменту** (переделке не подлежит): серверная сборка,
  URL вида `/moskva/ploshchadki/nazvanie/`, автозаголовки из данных карточки,
  открытая пагинация.

## Изображения — обязательная оптимизация (не подлежит забвению при росте каталога)

Каталог вырастет до тысяч фотографий подрядчиков и площадок — правило ставим один раз
сейчас, а не чиним задним числом на живом трафике.

- **Никакого сырого `<img src="...">` на фото карточек, галерей и геро-кадров.**
  Только `<Image>` / `<Picture>` из `astro:assets` — Astro сам пережимает файл,
  режет под нужные ширины (`widths`) и отдаёт `srcset`. Точечное исключение —
  чисто декоративные иконки/SVG, это не фото.
- **Источник — `src/assets/...`, не `public/`.** `import.meta.glob` и оптимизация
  Sharp работают только с файлами внутри `src/`; всё, что лежит в `public/`,
  отдаётся как есть, байт в байт, без сжатия и `srcset`.
- **Реестр `src/lib/images.ts`** (`resolveImage(path)`) — единая точка входа:
  данные (`feed.ts`, `specialists.ts`, `venues.ts`) как хранили фото строкой-путём
  (`/venues/river-loft/gal/g4.webp`), так и хранят — компонент/страница на выводе
  прогоняет путь через `resolveImage()` и получает `ImageMetadata` для `<Image>`.
  Новая категория подрядчиков — фото просто кладутся в `src/assets/...` по тому же
  пути, реестр подхватывает их автоматически, велосипед из нового `import.meta.glob`
  на каждой странице не нужен.
- **Всегда указывать `widths` и `sizes`**, а не один фиксированный размер: браузер
  должен получать кадр под свою колонку сетки, а не полноразмерный оригинал,
  сжатый только «в целом». `sizes` — реальная доля экрана, которую кадр занимает
  на каждом брейкпоинте (совпадает с `grid-template-columns` этого блока), не «на глаз».
- **`widths` не пишем массивом от руки — берём роль из `IMG_WIDTHS`**
  (`src/lib/images.ts`): `hero` (кадр во всю ширину), `wide` (широкий кадр
  в контенте), `card` (карточка каталога), `tile` (плитка доски), `stage`
  (полноэкранная сцена), `thumb` (метка, логотип). Наборы от руки уже один раз
  разъехались: у карточки площадки потолок был 1800, у такой же карточки
  специалиста — 1200, и на телефоне при DPR 2 кадр растягивался из 1200
  в ~1700 реальных пикселей и заметно мылил. Нужна новая роль — добавляем её
  в реестр, а не литерал в компонент.
- **Потолок `widths` не утяжеляет страницу.** Браузер берёт из `srcset` ОДНУ
  ширину — по `sizes` и своему DPR; телефон с узкой колонкой возьмёт 360 и при
  потолке 1800, и при потолке 800. Лишняя большая ширина стоит только места
  в сборке. Поэтому качество держим потолком под самый большой возможный показ
  кадра, а вес — честным `sizes`. Занижать потолок «ради скорости» — значит
  выдавать растянутый кадр всем, у кого экран крупнее.
- **В `src/assets` кладём материал, а не результат.** Сжимать кадр перед укладкой
  в репозиторий нельзя: Astro пережмёт его ещё раз под каждую ширину `srcset`,
  и сжатие ляжет поверх сжатия — получается мыло, которого не исправить ни
  `widths`, ни `sizes`. Ориентир для фотографии: длинная сторона **2400–3000 px**,
  webp quality **88** (≈600–900 КБ на кадр — столько весят кадры площадок).
  `srcset` физически не выдаст больше, чем лежит в исходнике.
- **Постер ролика — обычное фото, а не «кадр видео».** Сам ролик остаётся 720p
  (потолок VIDEO.md — про воспроизведение), но постер вырезаем из оригинала
  в 1080×1620: в первом экране карточки именно он и есть то, что человек видит
  до старта воспроизведения.
- **Битый файл в `src/assets` тихо доезжает до сайта.** Sharp не может пережать
  повреждённый webp и копирует его в сборку как есть — страница показывает
  обрезанный кадр, а сборка проходит зелёной. Так на сайте больше месяца жил
  `river-loft/gal/g13.webp`. Добавили пачку кадров — прогоняем по ним
  `magick identify`, прежде чем ставить их в данные.
- **`public/` — только для того, что обязано быть стабильным сырым URL**: OG-картинка
  для соцсетей (`og:image` собирается через `new URL(...)`, ей нужен литеральный путь),
  favicon и подобное. Не место для фото карточек «на всякий случай» —
  дублирование одного и того же пула в `public/` и `src/assets/` уже один раз
  ловили как баг (страницы ссылались на публичный путь, файл жил только в `src/assets`).
- **Когда фото переедут на сервер/CDN** (реальные подрядчики вместо демо-данных) —
  это меняет механизм, не отменяет правило. Локальный пайплайн `astro:assets` пережимает
  только файлы, которые физически лежат в `src/` на момент сборки; фото из БД/бэкенда
  так обработать нельзя. На тот момент нужен один из: (а) Astro `image.remotePatterns` +
  `<Image>` по внешнему URL, (б) готовый тумбнейл/CDN-сервис на стороне бэкенда
  (сам режет размеры и формат, отдаёт готовый `srcset`). Выбор — отдельное архитектурное
  решение к моменту подключения бэкенда, но сама привычка «фильтр/карточка получает уже
  готовый оптимизированный кадр, а не сырой файл» переносится без изменений.
- Сжатие не должно быть на глаз «пожёстче»: доверяем дефолтному качеству Sharp
  (~80) — это баланс, подобранный для фото, а не повод дожимать вручную и ловить
  артефакты. Если конкретный кадр всё равно тяжёлый после `astro:assets` — проверить
  не пережатие, а сам оригинал (реальное разрешение, битый файл).

### Пропорции фото — система на весь каталог, не разбор каждого кадра

Каталог вырастет до тысяч фото, отсматривать каждое при вёрстке не будем —
значит показ фотографии не должен зависеть от того, кто именно её проверил
на глаз. Два правила держат это без ручной проверки:

- **Открытая фотография — всегда в своей настоящей пропорции, без общего
  окна.** Первый экран площадки (`VenueHero`) и доска на главной (`PhotoBoard` /
  `lib/gallery`) не кроят кадр под одну рамку (`object-fit: cover` в
  фиксированном контейнере) — так один горизонтальный студийный кадр
  однажды обрезало сверху и снизу пополам, пока соседние вертикальные
  сидели в той же рамке нормально. Реф. Pinterest: открытая фотография
  показывается в СВОЁМ соотношении сторон, доска — тем более.
- **Вертикальность — одна граница на весь проект**, `isPortrait()` /
  `PORTRAIT_MAX_RATIO` в `lib/media.ts`. Раньше то же число жило только
  внутри доски, а первый экран площадки при выборе дежурного кадра считал
  вертикальность на свой лад — с ростом каталога такие развилки в двух
  местах не отсматриваются, они тихо накапливаются. Кому нужно «это
  вертикальный кадр?» — импортирует функцию, второго числа не заводит.
- **Мобилка — главный сценарий, значит горизонтальным в галерее площадки
  в целом не место.** Правило на будущее при заведении фото новых
  площадок/подрядчиков: галерея курируется вертикальными и квадратными
  кадрами по умолчанию, горизонтальный — исключение (широкий панорамный
  кадр внешнего вида и т.п.), не норма. Тогда любой кадр, по которому
  нажали в доске или в галерее, открывается вертикально и во весь экран
  телефона сам по себе — не нужно её отдельно подбирать под первый экран.
- **Портрет автора — своё поле `avatar`, а не кадр из галереи.** Кадры
  карточки это разные вещи в разных категориях: у ведущего в `photos` он
  сам, а у фотографа, видеографа, декоратора — его РАБОТЫ, и человека,
  с которым предстоит иметь дело, не видно нигде. Вырезать лицо из
  портфолио нельзя: свадебный кадр ростовой, квадратный кроп даёт грудь.
  Портрет присылает подрядчик отдельным файлом, кладём в
  `src/assets/specialists/<категория>/avatars/<slug>.webp` (квадрат,
  лицо в центре, от 400 px). Рисует всегда компонент `Avatar` — своих
  кружков по страницам не заводим: нет портрета, он сам ставит инициалы.
  На визитке кружок стоит всегда (слот держит вёрстку), в сетке каталога
  — только с реальным фото: кружок с буквами на каждой карточке шум.
- **Десктоп этим заходом не занимались** — первый экран площадки на ПК
  сейчас просто ограничен по высоте (`max-height`, `object-fit: contain`),
  чтобы вертикальный кадр не превращался в отвесную полосу на два экрана.
  Постоянное решение под широкий экран (например, коллаж из двух кадров
  рядом) — отдельная задача, не сейчас.

## Видео

Ролики в проекте есть и лежат в ленте (`data/reels.ts`, `public/reels/*.mp4`,
постеры — `src/assets/reels/*.webp`). Видео — не отдельная фича, а один из
кадров карусели: в `media` рядом с фотографиями стоит путь к ролику.

**Все правила и готовые команды пережатия — в `VIDEO.md`.** Оттуда же главное,
что нельзя забыть: Astro видео НЕ пережимает (в отличие от фото), поэтому файл
готовится заранее — немой луп 6–8 секунд, H.264, потолок 720p, 1–2 МБ,
и обязательный постер тем же путём с расширением `.webp`.

Ролики общего потока пока ни к кому не привязаны — это демо-набор без
карточки-источника, поэтому плитка с ними никуда не ведёт. При заведении
реальных подрядчиков привязку сделать обязательно, иначе чужое видео уедет
в продакшн как работа конкретного специалиста.

## Ловушка CSS: `X :global(Y)` между компонентами на одной странице

Реальный баг, отловлен на карточке площадки, час на диагностику — записано,
чтобы не наступать снова.

Когда ДВА разных компонента, оба попавшие на одну страницу, каждый пишет
`.свой-класс :global(.чужой-класс) { … }` (переопределяют что-то у чужого
компонента снаружи — так делали для `.prail`/`.prail-wrap` из `PhotoRail`
в нескольких местах), минификатор CSS на сборке иногда схлопывает правила
с одинаковым телом объявления в один селектор-список и **теряет scope-атрибут
у части селекторов**. Само чужое имя класса (`.prail`) в бандле страницы
становится полностью глобальным, без привязки к компоненту, который его
писал. Специфичность обычно всё равно защищает (голое `.prail` слабее
`.мой-компонент[cid] .prail`), но не всегда — итог непредсказуем и не виден
в исходниках, только в собранном CSS.

**Правило: не переопределять внутренности чужого компонента через
`:global()` снаружи, если от результата зависит вёрстка (размер, пропорция).**
Вместо этого — проп на самом компоненте, который включает нужный режим
изнутри (стили при этом лежат в том же компоненте, никакого `:global()`
снаружи). Старые `:global(.prail)`-переопределения (`ScrollyScenes`,
`ArticleVenues`, `PhotoBoard`, `phero__media` у специалиста) трогать по
мере необходимости, но новых таких не заводить.

**Смежная (тогда же пойманная) причина той же категории поломок —
циклическая процентная высота во flex.** Родитель `flex: 1 1 auto`,
а внутри — цепочка `height: 100%` до самой фотографии: браузер, чтобы
посчитать «естественный» размер родителя (basis: auto), обязан сперва
посчитать размер начинки, а начинка хочет 100% от ещё не посчитанного
родителя. Круг браузер рвёт молча — процент внутри в этот момент
читается как auto, и то, что должно было заполнить родителя, садится на
свой природный размер (у фото — по intrinsic-пропорции). Если процентная
высота внутри flex-элемента всё-таки нужна — **`flex: 1 1 0`, не `1 1 auto`**:
при flex-basis:0 браузер не трогает содержимое, чтобы посчитать размер, —
элемент считается только через flex-grow, число известно сразу и без
круга, а проценты внутри после этого резолвятся нормально. (Первый экран
площадки, где это всплыло, от самой идеи «кадр забивает высотой родителя»
в итоге отказался — см. `VenueHero.astro`: кадры там разной пропорции, и
общее окно с cover резало студийные фото по сюжету. Приём с `flex: 1 1 0`
остаётся верным на будущее для мест, где растянуть кадр на 100% родителя
всё же нужно.)

## Дизайн-система (нарушать нельзя)

- **Все значения — токены** из `src/styles/global.css`. Хардкод цветов, отступов,
  скруглений и длительностей в компонентах запрещён. Новая ручка нужна — добавь токен.
- **Реестр готовых элементов** (сначала ищем здесь, только потом создаём новое,
  и новое — сразу в global.css, а не в стилях страницы):
  - `.pill` (+ `--lg`, `--sm`) — единственная кнопка/ссылка-действие проекта;
  - `.chip` (+ `--icon`, `__count`, `__badge`, обёртка `.chip-opt` над чекбоксом) —
    плашка-состояние в фильтрах: заливка `--surface` без обводки, включённая —
    чернильная инверсия. `.pill` — действие, `.chip` — выбор;
  - `.sheet` (+ `__backdrop __panel __head __title __body __foot`, `--dock`) —
    нижняя шторка для любой настройки на телефоне; `--dock` на ПК превращает
    её в постоянную колонку слева. Открытие — `src/lib/sheet.ts` (`bindSheet`);
  - `.radio-row` / `.radio-list` — строка «один из» с кружком (сортировка,
    локация в шторке);
  - `FilterBar.astro` + `FilterSheet.astro` — фильтрация каталога: полоса чипов
    над сеткой (телефон) и шторка/колонка фильтров (см. `DESIGN.md`);
  - `.icon-btn` — круглая кнопка-иконка (аккаунт, назад);
  - `.t-display .t-h1 .t-h2 .t-lead .t-small .t-caption .t-num` — типографика;
  - `.media` — фото-контейнер; `.veil` — затемнение кадра (см. правило ниже:
    под текст его больше не используем, осталось только под иконки);
  - `.save` — сердце «в избранное» поверх кадра; оживляет `lib/save.ts`
    (`bindSaveButtons`), снимок карточки — `lib/favorite-snapshot.ts`;
  - `.theme-dark` — инверсия секции: внутри неё `.pill`/`.icon-btn` сами
    становятся белыми (всё через `--bg`/`--fg`, руками не красить);
  - `--shadow-float` — тень парящих капсул; `--surface-dim` — подложка фото;
  - `BottomDock.astro` — нижнее меню, одно на все страницы;
  - `EntryRail.astro` — цветной ряд входов в разделы на главной: тона
    `--tint-*` / `--tint-*-deep`, единственное место со скруглением плиток
    (`--radius-tile-soft`); склонение при числе — `lib/plural.ts`
    (см. `DESIGN.md`).
- **Текст НЕ лежит на фотографии.** Ни названий, ни цен, ни подписей, ни
  счётчиков — всё это живёт на бумаге под кадром (первый экран площадки,
  карточки каталогов, входы в разделы на главной, подборка в статье).
  Подпись поверх кадра всегда требует вуали, зависит от того, что попало
  в угол снимка, и на светлых фото тонет. На кадре допустимы только иконки
  со своей тенью — сердце `.save`. Точки-индикаторы карусели — строкой
  ПОД кадром, серыми (`PhotoRail`), а не на нём.
- Приглушение белого на тёмном — только `opacity` на элементе,
  не `rgb(255 255 255 / …)` россыпью по страницам.
- Шрифт **Onest**. Плотный набор: вес всего сайта задают четыре токена —
  `--w-body` (корпус) / `--w-medium` (служебное) / `--w-head` (заголовки) /
  `--w-head-lg` (h1 и display). Своих `font-weight` в компонентах нет.
  Тонких начертаний в проекте не осталось.
  **Капс запрещён** везде.
- Палитра: кремовая бумага `--paper` / тёплый чёрный `--ink` / алый `--accent`.
  Цвет ровно один — алый: заливка плашек (`.theme-accent`) и акцентный набор
  заголовка. Инверсия секции — классом `.theme-dark`, акцентная плашка —
  `.theme-accent` (семантические `--bg`/`--fg`), не ручными цветами.
- Кнопки — пилюли `.pill` (radius 999px, обводка 1px, hover-инверсия).
- Логотип `public/logo.svg` нарисован белым и красится маской
  (`mask: url('/logo.svg')` + `background: var(--ink)`), а не фильтром:
  `brightness(0)` даёт чистый `#000` мимо палитры.
- Типографические роли — классы `.t-display .t-h1 .t-h2 .t-lead .t-small .t-caption`.
- Фото — через `.media` (object-fit cover, скругление из `--radius-media`).

## Mobile-first (главное правило вёрстки)

- **Весь фокус — на мобилку.** Базовая вёрстка и дизайн-решения — под телефон
  (~375–430px); десктоп — прогрессивное расширение, медиазапросы только
  `min-width`. Референсы могут приходить из мобильных приложений.
- **Моушн-бюджет мобилки:** только transform/opacity, без blur/filter-анимаций,
  без тяжёлых канвасов и параллаксов на телефоне. На мобиле токены сами
  укорачивают анимацию (см. media-блок в global.css).
- **Вау-эффекты — только на широком экране:** всё «дорогое» заворачивать в
  `@media (min-width: 1024px) and (pointer: fine)`. Ховер-эффекты — только под
  `@media (hover: hover)` (на тач-экране ховера нет).
- Lenis не трогает нативный тач-скролл (по умолчанию) — на телефоне скролл
  системный, безупречный; плавность Lenis — десктопный бонус.

### Навигация: сценарий мобилки и десктопа — не один UI

Mobile-first задаёт вёрстку, но не значит «одна и та же навигация везде,
только сжатая». У мобилки и десктопа разные способы вернуться назад —
жест/системная кнопка на телефоне, мышь и клавиатура на ПК — и решение
должно быть разным по существу, не одной уменьшенной копией.

- **Карточка-«потомок» (провалились из каталога вглубь: площадка,
  специалист, статья блога) — навигация «назад», не хлебная крошка
  текстом.** Крошка текстом — паттерн сайта с постоянной шапкой; у нас
  шапка скрыта (см. `SiteHeader.astro`, `display: none` на время
  дизайн-фазы), а сама строка «Главная / Площадки / …» поверх фото или
  над ним съедала экран и на телефоне читалась как мусор перед главным —
  самой площадкой.
- **Компонент `BackButton.astro`** — круглая ink-капсула поверх кадра
  (тот же язык, что у метки на карте: чернильная подложка читается на
  любом фото). Ставится там, куда попадают вглубь, а не через нижний
  док: `VenueHero`, `phero` специалиста. Раздел из нижнего дока
  («Площадки», «Специалисты», «Избранное») — это не потомок, ему кнопка
  «назад» не нужна, он сам корень своей ветки.
  Ссылка настоящая (`href` на раздел-родитель) — переход по ней остаётся
  в HTML и работает без JS; клиентский скрипт поверх подменяет его на
  `history.back()`, если у вкладки есть история этого же сайта (обычный
  путь — пришли из каталога), и оставляет обычный переход по ссылке,
  если попали прямым заходом (поиск, закладка — истории нет).
- **Внутренняя перелинковка на раздел не потеряна** — она живёт в самом
  `href` кнопки «назад», просто без видимого текста «Площадки» рядом.
  Микроразметка `BreadcrumbList` (задача в `SEO.md`, п. про заготовки)
  не завязана на видимую крошку — это отдельный `<script type="application/ld+json">`
  в `<head>`, ставится независимо и решает то же для поисковика.
- **Не сделано (следующий шаг, не сейчас):** блог ещё не переведён на
  тот же паттерн — там крошка живёт на бумаге, а не на фото, поэтому
  конфликта нет и трогать не пришлось. Отдельного «десктопного» вида
  навигации (постоянная верхняя шапка, крошки текстом при мыши) тоже
  пока нет — `SiteHeader` выключен целиком до конца дизайн-фазы, и когда
  его будут включать, разводить мобилку/десктоп заново по этому же
  принципу, а не чинить одним общим компонентом.

## Моушн (в основе всего)

- Плавный скролл — Lenis, инициализирован в `Layout.astro`. GSAP установлен для
  сложных сцен.
- Появление блоков: `data-reveal` на элементе, `data-reveal-group` на родителе
  (каскад детей). Никаких ручных transition — токены `--dur-*` / `--ease-*`.
- Никакого «топорного» моушна: linear и ease-in-out по умолчанию не использовать,
  только `--ease-out` (expo) / `--ease-inout`. `prefers-reduced-motion` уважается
  автоматически (глобальный guard в global.css).

## Рабочий режим

**Фаза: дизайн-прототип фронта.** Сейчас отрабатываем не продакшн, а сценарии:
как выглядит, куда кликается, куда проваливается. Приложение строится большое,
эту вёрстку потом переработаем — поэтому:

- **Быстрые целенаправленные итерации.** Просят поправить элемент, присылают
  скриншот — делаем сразу, без разведки и раздумий.
- **На внутрянку усилий не тратим.** Клиентская логика, интеграции, бэкенд —
  после дизайна. Временные заглушки помечаем комментарием в коде.
- **Но структуру формируем сразу грамотно**, чтобы на неё быстро легла
  функциональность: данные отдельно от вёрстки, типы как будущая схема БД,
  компоненты переиспользуемые.
- **Каждая находка — во внутренний документ, это главное правило фазы.**
  Разборы конкурентов, SEO-схемы, паттерны и сценарии не остаются в чате:
  `SEO.md` — продвижение (разбор конкурента wedwed.ru, схема блог → подборка → карточка,
  долги по внутрянке); `SPACING.md` — сетка и отступы.
- Быстрые правки (шрифт, композиция, цвет) — просто делаем, БЕЗ запуска Playwright
  и скриншотов. Браузерную проверку подключаем только для сложных вещей по просьбе.
- Пользователь присылает скриншоты-референсы — внимательно разбирать и точно повторять.
- Вьюпорт пользователя ~1280 CSS px (Windows-масштаб 150%): его скриншоты делить на 1.5.

## Хостинг и деплой (боевой сервер, с 01.09.2026)

Сайт живёт на **облачном VPS Timeweb**, домен **wed-secrets.ru** (регистратор
reg.ru, NS остались регруйными). GitHub Pages отключён — вместе с ним ушёл
костыль `base=/wedwibse/` и переписывание путей регулярками: на своём домене
сайт живёт в корне, `base` всегда `/`.

Общая процедура (новый сервер, другой проект, SSL, зеркала, разбор поломок) —
в скилле `timeweb-vps-deploy`. Здесь только конкретика этого проекта.

| Что | Значение |
| --- | --- |
| Сервер | `193.124.47.78`, IPv6 `2a03:6f00:a::2:c0f3`, Ubuntu 26.04, нода `kvmnvm-760` |
| Каталог сайта | `/var/www/wedsecrets` (владелец `deploy:www-data`) |
| Конфиг nginx | `/etc/nginx/sites-available/wedsecrets` |
| Админский вход | `ssh -i ~/.ssh/timeweb_wed root@193.124.47.78` |
| Деплой-пользователь | `deploy` — доступ только к каталогу сайта |
| Root-пароль | в `.env` проекта (в `.gitignore`), в чат и в код не попадает |

**Обновление сайта — только пушем в master.** [deploy.yml](.github/workflows/deploy.yml)
собирает на раннере и заливает `rsync --delete` под пользователем `deploy`,
примерно минута от пуша до сайта. Руками на сервер ничего не копировать:
следующий деплой всё равно перезатрёт, а права на файлы сломаются
(заливка под root делает файлы недоступными для `deploy`).

**Сборка на сервере не идёт**, Node там нет и не нужен — это осознанно:
2 ГБ RAM тратятся на отдачу статики, а не на `npm ci`.

**Сайт закрыт от поисковиков** — три слоя и порядок снятия описаны
в `SEO.md`, раздел 5. Флаг сборки `SITE_INDEXABLE`, по умолчанию закрыто.
